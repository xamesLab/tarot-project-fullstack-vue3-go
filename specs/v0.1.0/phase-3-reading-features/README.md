# Этап 3. Tarot-функциональность

## Цель этапа

Реализовать основной пользовательский сценарий продукта: получение дневной карты, генерацию 3-карточных раскладов, отображение лимитов и просмотр истории чтений.

## Что должно быть реализовано

### 1. Backend для чтений

- модель чтения и карточки в чтении
- репозиторий чтений
- сервис генерации:
  - `GenerateCardOfDay`
  - `GenerateThreeCardSpread`
  - `GetReadingHistory`
- endpoint history
- хранение `accounting_date`, `timezone`, `deck_id`, `expires_at`

### 2. Детерминированная дневная карта

- seed на основе `user_id + accounting_date + timezone`
- одна карта в сутки на учётный день
- защита от повторной генерации
- возврат времени следующего сброса

### 3. Ролевые лимиты

- чтение `role_policies`
- расчёт доступного остатка по `3-card spread`
- блокировка генерации при достижении лимита
- учёт reset после смены `accounting day`

### 4. Frontend-компоненты tarot

- `TarotCard`
- `CardOfDay`
- `ThreeCardSpread`
- отображение:
  - имени карты
  - интерпретации
  - тегов
  - remaining count
  - loading и error states

### 5. Dashboard

- автоматическая загрузка актуального состояния
- генерация карты дня
- генерация расклада
- показ остатка лимитов
- обработка first-time user flow

### 6. История

- `ReadingHistory` component
- страница `/history`
- фильтрация по типу
- пагинация
- разворачивание деталей
- отображение срока хранения истории

## Результат этапа

После этого этапа пользователь уже получает полный core experience продукта и может использовать сервис по основному сценарию MVP.
