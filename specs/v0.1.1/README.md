# План разработки v0.1.1

Этот каталог содержит план следующей продуктовой итерации `Nebula Tarot`, идущей поверх завершённого baseline `v0.1.0`.

Главная цель `v0.1.1`:

- подключить AI-модель напрямую через `OpenRouter API`
- сделать прямое подключение основным рабочим путём в обход текущего `gateway stub`
- сохранить архитектурную возможность, чтобы в следующих версиях `gateway` стал fallback-каналом
- не включать deployment в scope этой версии

План опирается на:

- `specs/docs/PRD.md`
- `specs/docs/TECHNICAL_SPEC.md`
- `specs/docs/IMPLEMENTATION_ROADMAP.md`
- `specs/docs/DESIGN_SYSTEM.md`
- `specs/v0.1.0/README.md`

Каждый этап, как и в `v0.1.0`, оформлен отдельной папкой и включает:

- `README.md` — цель, объём работ, результат и критерии готовности
- `MANUAL_TESTS.md` — ручная приёмка этапа
- `AI_AGENT_PLAN.md` — ориентир для агентной реализации

## Этапы

1. `phase-0-ai-foundation` — подготовка архитектуры, конфигурации и модели данных для прямой AI-интеграции
2. `phase-1-openrouter-direct-backend` — backend-интеграция `OpenRouter` как primary provider
3. `phase-2-ai-reading-experience` — подключение AI-интерпретаций в пользовательский интерфейс
4. `phase-3-admin-controls-and-quality` — админ-контроль AI-функции, лимиты, улучшение UX и наблюдаемости
5. `phase-4-polish-and-manual-testing` — стабилизация, edge cases и финальная ручная приёмка версии

## Принципы версии

- direct `OpenRouter` path считается основным для `v0.1.1`
- `gateway` не удаляется, но не используется как primary path
- интеграция должна быть спроектирована так, чтобы в будущем direct path можно было опустить до fallback-режима
- значения секретов и API-ключей не должны попадать в документацию, логи и frontend bundle
- frontend должен оставаться синхронизированным с `UI Kit` и общей дизайн-системой
- rollout в production не входит в scope этой версии

## Базовые env-параметры

Для backend уже подготовлены секреты и модельные параметры, которые должны использоваться без публикации их значений:

- `OPENROUTER_KEY`
- `OPENROUTER_MODEL_MAIN`

При необходимости в рамках реализации допускается добавить новые non-secret параметры конфигурации, но без фиксации секретных значений в документах.

## Внешние reference-материалы

Для `v0.1.1` архитектурные решения должны учитывать актуальную официальную документацию `OpenRouter`:

- chat completions API: `POST /api/v1/chat/completions`
- API overview и OpenAPI schema
- models API для синхронизации/валидации доступных моделей
- attribution headers `HTTP-Referer` и `X-OpenRouter-Title` / `X-Title`

## Ожидаемый результат версии

После завершения `v0.1.1` продукт должен:

- уметь получать AI-интерпретации раскладов напрямую через `OpenRouter`
- сохранять результаты и метаданные запросов на backend
- показывать AI-результаты в пользовательском интерфейсе без нарушения существующего reading flow
- предоставлять базовые лимиты, контроль, диагностику и ручную проверку качества
- сохранять готовность к будущему переходу на схему `gateway primary / direct fallback`

## Базовый пользовательский AI-flow

В `v0.1.1` frontend должен реализовывать AI-интерпретацию так:

- пользователь открывает `Card of the Day` или все карты `3-card spread`
- после этого frontend инициирует backend-запрос к AI endpoint
- backend отправляет запрос модели через `OpenRouter`
- результат возвращается в приложение и отображается в уже существующем блоке `Значение расклада`
- после успешной генерации результат сохраняется у самого `reading`, чтобы по одному и тому же раскладу не отправлять множество одинаковых запросов

AI-слой не должен создавать отдельный конкурирующий экран или новый тип reading view. Он дополняет текущий flow раскрытого чтения.

## Базовое правило prompt-а

Для первого релиза `v0.1.1` prompt должен как минимум:

- включать тип чтения
- включать карты расклада
- для `3-card spread` включать позиции карт
- указывать, что ответ должен содержать только компактную интерпретацию расклада
- ограничивать длину ответа пределом до `100` слов

На уровне продукта это означает, что итоговый AI-ответ должен быть кратким, прикладным и не превращаться в длинное эссе.

## Правило сохранения результата

Для `v0.1.1` AI-ответ должен не только сохраняться в `ask_requests`, но и кэшироваться в самом `reading` как текущее актуальное значение для блока `Значение расклада`.

Это нужно для двух задач:

- не отправлять повторные запросы к модели для одного и того же уже обработанного расклада
- быстро восстанавливать AI-интерпретацию при повторном открытии dashboard/history без дополнительной генерации
