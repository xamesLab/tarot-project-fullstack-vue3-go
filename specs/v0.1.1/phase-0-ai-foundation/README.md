# Этап 0. AI foundation

## Цель этапа

Подготовить архитектурную основу для AI-интеграции так, чтобы `OpenRouter` можно было подключить напрямую без слома существующего backend и без жёсткой привязки продукта к одному transport path.

## Что должно быть реализовано

### 1. Архитектурное решение

- зафиксировать, что в `v0.1.1` primary provider path — direct `OpenRouter`
- сохранить абстракцию, позволяющую позже вернуть `gateway` как primary path и использовать direct path как fallback
- определить provider-слой, который не зависит от handler-ов и UI

### 2. Конфигурация backend

- расширить `config.Config` полями для AI-провайдера
- подключить чтение env-параметров `OPENROUTER_KEY` и `OPENROUTER_MODEL_MAIN`
- при необходимости добавить non-secret параметры:
  - base URL
  - timeout
  - app title / referer
  - feature flag для direct AI
- убедиться, что значения секретов не попадают в ответы API, panic messages и логи

### 3. Модель данных

- актуализировать использование коллекции `ask_requests`
- добавить в `daily_readings` поле для сохранённой AI-интерпретации как текущего кэша результата
- расширить запись запроса полями:
  - `provider`
  - `model`
  - `prompt_version`
  - `status`
  - `reading_id`
  - `user_id`
  - `requested_at`
  - `completed_at`
  - `error_code`
  - `error_message`
  - `usage`
  - `response_excerpt`
- предусмотреть хранение raw-ответа только если это не нарушает privacy и не создаёт лишний риск утечки
- зафиксировать, что `ask_requests` хранит историю запросов, а `daily_readings.ai` хранит последний актуальный результат для повторного отображения без нового вызова модели

### 4. API-контракт

- определить финальный контракт для:
  - `POST /api/ask`
  - `GET /api/ask/:request_id`
- решить, возвращает ли `POST /api/ask` сразу готовую интерпретацию, статус + payload или только `request_id`
- зафиксировать идемпотентность повторного запроса для уже обработанного чтения

### 5. Правила безопасности

- не логировать ключи и полный prompt c чувствительными полями
- валидировать доступ пользователя к `reading_id`
- не допускать AI-запрос к чтению другого пользователя
- определить лимит повторной генерации и правила reuse уже существующей интерпретации
- определить приоритет чтения данных: сначала `daily_readings.ai`, потом `ask_requests`, только затем новый provider request

## Результат этапа

После этапа проект получает устойчивую основу для подключения прямого AI-провайдера, не раскрывая секреты и не создавая тупиковую архитектуру.

## Основные риски этапа

- прямое связывание handler-ов с внешним AI API
- утечка секретов через логи или ошибки
- слабый контракт `ask_requests`, который потом сложно расширять
- отсутствие задела под будущий fallback через `gateway`

## Критерии готовности

- provider abstraction зафиксирована
- env-конфигурация описана и безопасна
- структура `ask_requests` обновлена под реальный AI-flow
- `daily_readings` готово хранить текущую AI-интерпретацию чтения
- API-контракт `/api/ask` определён
- секреты не фигурируют в документации и логических примерах
