# Этап 1. Direct OpenRouter backend

## Цель этапа

Подключить `OpenRouter` напрямую на backend как основной AI provider для `v0.1.1` и превратить stub-эндпоинты в рабочий AI flow.

## Что должно быть реализовано

### 1. HTTP-клиент провайдера

- реализовать direct client для `OpenRouter`
- использовать `POST /api/v1/chat/completions` как основной endpoint
- передавать `Authorization: Bearer ...`
- передавать `Content-Type: application/json`
- при необходимости добавить attribution headers:
  - `HTTP-Referer`
  - `X-OpenRouter-Title` или совместимый `X-Title`

### 2. Работа с моделями

- использовать `OPENROUTER_MODEL_MAIN` как основной model id
- предусмотреть валидацию модели через models API или на startup/runtime health-check уровне
- не зашивать model id в код

### 3. Prompt execution

- собрать prompt для AI-интерпретации на основе:
  - типа чтения
  - открытых карт
  - позиции карты в раскладе
  - текущего языка пользователя
- отдельно указать модели, что нужен только компактный итоговый текст без вступлений, списков и дисклеймеров
- ограничить целевую длину ответа до `100` слов
- добавить versioning prompt-шаблонов
- фиксировать prompt version в `ask_requests`

Минимальное требование к prompt для `v0.1.1`:

- `Card of the Day`: передавать карту и язык ответа
- `3-card spread`: передавать все карты, их позиции и язык ответа
- явно требовать только компактную интерпретацию расклада
- запрещать модели уходить в длинное объяснение, повторять названия секций и добавлять лишние форматы ответа

### 4. Ответ AI

- извлекать итоговый текст интерпретации из ответа провайдера
- сохранять status, usage и provider metadata
- валидировать ограничение краткости и нормализовать ответ перед возвратом на frontend
- после успешного ответа сохранять итоговую AI-интерпретацию в `reading.ai`, чтобы повторные запросы по тому же раскладу не шли в модель без необходимости
- обрабатывать:
  - timeout
  - `401`
  - `429`
  - `5xx`
  - пустой/невалидный ответ модели

### 5. Backend endpoints

- превратить `POST /api/ask` в рабочий endpoint
- превратить `GET /api/ask/:request_id` в рабочий endpoint статуса/результата
- сохранить авторизацию и привязку к владельцу чтения
- зафиксировать, будет ли запрос синхронным или pseudo-async через persisted status lifecycle
- при повторном запросе сначала проверять сохранённый AI-результат у `reading` и только потом решать, нужен ли новый provider call

### 6. Health и диагностика

- добавить backend-level health/readiness для AI provider
- не смешивать это с legacy `gateway stub`, если это ломает ясность
- оставить диагностический путь для direct AI без раскрытия секретов

## Результат этапа

После завершения этапа backend сможет напрямую получать AI-интерпретации через `OpenRouter`, сохранять результат и возвращать его через собственный API.

## Основные риски этапа

- ошибки маппинга ответа `OpenRouter` в наш domain contract
- нестабильность prompt-output формата
- отсутствие нормального retry/backoff на сетевых ошибках
- рост затрат при повторной генерации без reuse

## Критерии готовности

- `POST /api/ask` работает через real provider
- `GET /api/ask/:request_id` отдаёт реальный status/result
- usage и provider metadata сохраняются
- ошибки провайдера отображаются безопасно и предсказуемо
- ключ и secret-параметры не утекают в API или логи
