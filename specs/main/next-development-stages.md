## 2. Ближайшие этапы разработки

### Этап `v0.1.4`

Цель:
- объединить ближайшие задачи post-`v0.1.3` в единый реализуемый этап без блока автотестов и без блока файлового storage до отдельного явного запроса пользователя.

Что сделать:
- поднять backend в рабочем окружении;
- обеспечить доступность Gateway и callback security конфигурации;
- выполнить `deploy/scripts/smoke-v0.1.2-ask.ps1`;
- добавить `/dev` как индекс внутренних dev-only страниц;
- подготовить структуру для расширения dev-инструментов;
- начать перенос продуктовых экранов на токены и паттерны `/ui-kit`;
- добавить cleanup-скрипт для smoke-данных (`v011*`, `smoke*`, тестовые колоды);
- оформить повторяемый сценарий очистки после smoke-прогонов;
- обновить статусные документы `v0.1.2` по результату smoke-прогона.

Результат этапа:
- подтвержденный end-to-end ask-flow для `v0.1.2`;
- dev-tools и UI Kit workflow оформлены как следующий рабочий контур;
- меньше ручной зачистки данных;
- меньше риска накопления тестового мусора в окружении.

Приоритет:
- `high`

## 3. Следующий блок после `v0.1.4`

Цель:
- снизить технические риски хранения и эксплуатации.

Что сделать:
- задачи по файловому storage не запускать до отдельного явного запроса пользователя;
- подготовить вынос изображений в S3-совместимое object storage только после такого запроса;
- описать стратегию миграции URL и обратной совместимости только после такого запроса;
- добавить backup/restore runbook для MongoDB;
- подготовить changelog/release notes для версий после MVP.

Результат этапа:
- более зрелая эксплуатационная база проекта;
- подготовка к следующему функциональному расширению.

Приоритет:
- `medium`

## 4. Рекомендуемый порядок выполнения

1. Выполнять `specs/version-0.1.4/steps.md`.
2. После закрытия `v0.1.4` не возвращаться к автотестам и storage-задачам без отдельного явного запроса пользователя.
3. После отдельного запроса пользователя возвращаться к storage/runbook/release-notes задачам.
