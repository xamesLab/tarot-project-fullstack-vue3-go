# Рекомендации по рефакторингу и оптимизации backend

**Дата обзора:** 19 октября 2026 года  
**Область:** `backend/` — конфигурация, HTTP handlers, middleware, services, repositories, models, загрузка изображений и seed utility.  
**Тип обзора:** статическое чтение кода; приложение не запускалось, тесты и профилирование не выполнялись. Код приложения не менялся.

Документ фиксирует наблюдения и варианты улучшения, а не готовое техническое задание. Приоритеты обозначают порядок проверки и планирования. Перед изменениями, затрагивающими API, MongoDB или доступ, стоит сверить поведение с production-конфигурацией и контрактами frontend.

## Краткий итог

Слои handler → service → repository в целом разделены, ошибки API сведены к общему формату, Mongo-запросы получают контекст запроса, а загрузка ZIP проверяет структуру путей и содержимое изображений. Главный потенциал улучшения — в конкурентной корректности чтения и лимитов, строгой конфигурации безопасности, защите загрузок, горячих Mongo-путях и уменьшении ответственности крупных сервисов.

## Высокий приоритет

### 1. Сделать создание чтений и применение лимитов атомарными

В `GenerateCardOfDay` и `ResolveCardOfDay` сначала проверяется наличие чтения, затем создаётся документ; соответствующий индекс в `ReadingRepository.EnsureIndexes` не уникальный. При одновременных запросах пользователя могут появиться две карты дня. `GenerateThreeCardSpread` и `ensureAIAvailableForUser` также считают текущие документы, проверяют лимит, а затем создают новый запрос/расклад. Несколько параллельных запросов могут пройти одну и ту же проверку и превысить дневной лимит.

Ссылки: [reading.go:152](../../backend/internal/services/reading.go#L152), [reading.go:232](../../backend/internal/services/reading.go#L232), [reading.go:334](../../backend/internal/services/reading.go#L334), [reading.go:23](../../backend/internal/repositories/reading.go#L23), [ask.go:515](../../backend/internal/services/ask.go#L515), [ask.go:338](../../backend/internal/services/ask.go#L338).

**Рекомендация:** для карты дня закрепить уникальность на уровне MongoDB отдельным partial unique index по пользователю и расчётной дате для `card_of_day`; корректно обработать duplicate key как возврат уже созданного чтения. Для лимитов раскладов и AI использовать атомарную запись счётчика/резерва на пользователя и расчётный день либо транзакцию с проверкой лимита. Повторные запросы AI для одного чтения и языка сделать идемпотентными. До создания индексов проверить и разрешить существующие дубли.

### 2. Обновлять раскрытие карты атомарно, а не перезаписывать весь массив

`RevealReadingCard` читает документ, меняет `Viewed` в локальной копии `Cards`, затем сохраняет весь массив. Два одновременных раскрытия разных карт могут перезаписать изменения друг друга: последняя запись сохранит только один из флагов `Viewed`. Это может мешать последующему запросу AI-интерпретации, который требует раскрытия всех карт.

Ссылки: [reading.go:479](../../backend/internal/services/reading.go#L479), [reading.go:496](../../backend/internal/services/reading.go#L496), [reading.go:518](../../backend/internal/services/reading.go#L518), [reading repository:71](../../backend/internal/repositories/reading.go#L71), [ask.go:957](../../backend/internal/services/ask.go#L957).

**Рекомендация:** обновлять только конкретную позицию массива через positional update/array filters и проверять `MatchedCount`; если нужен ответ с актуальным чтением — возвращать документ после обновления. Альтернатива — optimistic concurrency с версией документа.

### 3. Ужесточить проверку JWT и немедленное применение изменений роли/статуса

В production конфигурация по умолчанию всё ещё задаёт известный development JWT secret. Режим `production` переключает Gin, но не заставляет задать собственный секрет. Обычная проверка токена не ограничивает допустимый signing algorithm явно; guest-токен такой проверки уже имеет. Middleware берёт роль из claims и не проверяет актуальный статус пользователя, поэтому уже выданный токен продолжит работать после блокировки аккаунта или снятия роли `keeper` до истечения TTL.

**Рекомендация:** при `APP_ENV=production` завершать запуск с ошибкой при отсутствующем/известном development secret; проверить положительный TTL и минимальную длину секрета. При разборе JWT разрешать только HS256. Выбрать явную политику отзыва: короткий TTL с повторной аутентификацией, версия сессии/токена или проверка статуса и актуальных прав в middleware (при необходимости с коротким кэшем). Отдельно проверить сценарии блокировки пользователя и понижения роли.

### 4. Ограничить ресурсы и публичный доступ при обработке загружаемых изображений

В `main.go` задан `MaxMultipartMemory` 256 MiB, но это порог памяти multipart-парсера, а не общий предел тела запроса. Валидация ограничивает размер файла, но не ширину/высоту и общее число пикселей. Затем `saveImageAsPNG` и `extractZipImageAsPNG` полностью декодируют изображение; небольшой сжатый файл с чрезмерными размерами может потребовать много памяти. Временные ZIP и изображения сохраняются в `uploads/temp`, а весь `uploads` смонтирован публично на `/uploads`, значит временный файл потенциально доступен по HTTP, пока обрабатывается.

Ссылки: [main.go:35](../../backend/main.go#L35), [main.go:36](../../backend/main.go#L36), [admin handler:120](../../backend/internal/handlers/admin.go#L120), [admin handler:178](../../backend/internal/handlers/admin.go#L178), [deck_upload.go:288](../../backend/internal/utils/deck_upload.go#L288), [deck_upload.go:313](../../backend/internal/utils/deck_upload.go#L313), [deck_upload.go:338](../../backend/internal/utils/deck_upload.go#L338).

**Рекомендация:** установить общий предел HTTP body и отдельные лимиты ZIP/картинки/числа записей; до полного декодирования ограничивать ширину, высоту и число пикселей. Хранить временные файлы вне публичного `uploads` и удалять их гарантированно. Добавить ограничения частоты для login/register и дорогостоящих публичных маршрутов на reverse proxy или в middleware.

## Средний приоритет

### 6. Убрать записи и лишние round trip из горячих read-путей

`AdminSettingsRepository.Get` при каждом чтении сначала вызывает `EnsureDefault`, а тот делает upsert в MongoDB, после чего выполняется ещё один `FindOne`. `ReadingService.buildReadingResponses` вызывает этот метод при сборке каждого ответа. Пути выбора default deck/back также читают settings отдельно. В `UserRepository` методы изменения профиля, настроек, роли и статуса выполняют `FindOneAndUpdate`, а затем отдельный `FindByID`, хотя MongoDB может вернуть обновлённый документ в первой операции.

Ссылки: [admin_settings.go:24](../../backend/internal/repositories/admin_settings.go#L24), [admin_settings.go:43](../../backend/internal/repositories/admin_settings.go#L43), [reading.go:563](../../backend/internal/services/reading.go#L563), [reading.go:679](../../backend/internal/services/reading.go#L679), [user.go:71](../../backend/internal/repositories/user.go#L71), [user.go:91](../../backend/internal/repositories/user.go#L91), [user.go:192](../../backend/internal/repositories/user.go#L192).

**Рекомендация:** оставить `EnsureDefault` на старте/миграции, а обычный `Get` сделать read-only. Для update-запросов включить `ReturnDocument(options.After)` и убрать повторное чтение. Измерить число запросов и latency основных сценариев до/после.

### 7. Сократить число запросов в админской статистике и истории чтений

`GetDashboardMetrics` последовательно делает 18 операций подсчёта по MongoDB. Каждый `CountSince` запускает три отдельных подсчёта, всего шесть для двух периодов. Эти выборки фильтруют только по `generated_at`, тогда как runtime-индекс истории чтений начинается с `user_id`; seed utility не создаёт отдельный индекс с ведущим `generated_at`. Поэтому на больших коллекциях метрики могут сканировать много документов.

При сборке истории карты ищутся одним `$in`-запросом, но рубашки читаются отдельным запросом для каждого уникального `backID`; проверка наличия файлов вызывает `os.Stat` для каждой карты.

Ссылки: [admin.go:51](../../backend/internal/services/admin.go#L51), [reading repository:150](../../backend/internal/repositories/reading.go#L150), [reading.go:563](../../backend/internal/services/reading.go#L563), [reading.go:841](../../backend/internal/services/reading.go#L841), [reading.go:829](../../backend/internal/services/reading.go#L829), [seed indexes:284](../../backend/deploy/seed/main.go#L284).

**Рекомендация:** заменить серию метрик на одну-две aggregation pipeline с группировкой по типу/периоду и согласовать индексы с реальными `explain`-планами. Для истории добавить batch lookup рубашек по ID; проверить, можно ли исключить per-card `stat` из построения ответа, опираясь на проверенные метаданные ассетов.

### 8. Согласовать кэш AI-карты дня с фактическим содержимым prompt

Ключ гостевого кэша строится из карты, языка и версии prompt. Сам prompt также включает дату расчётного дня и часовой пояс. Для той же карты и языка новый запрос может получить кэшированный результат, сгенерированный для другой даты/зоны. Ключ не включает выбранную AI-модель, хотя она сохраняется в записи кэша.

Кроме того, сохранённая пользовательская интерпретация карты дня возвращается по версии prompt, но без сравнения языка запроса с `reading.AI.Language`. После смены языка может вернуться текст на прежнем языке.

Ссылки: [ask.go:127](../../backend/internal/services/ask.go#L127), [ask.go:770](../../backend/internal/services/ask.go#L770), [ai_prompt.go:45](../../backend/internal/services/ai_prompt.go#L45), [ask.go:227](../../backend/internal/services/ask.go#L227), [ask.go:282](../../backend/internal/services/ask.go#L282).

**Рекомендация:** определить, должна ли интерпретация быть общей для пары карта-язык или зависеть от даты, зоны и модели. Если зависит — включить эти параметры в ключ, добавить срок хранения и миграционную версию; если не зависит — убрать динамические поля из prompt. Для пользовательских чтений хранить/кэшировать результат как минимум по `reading + language + prompt version` и проверять язык при повторном использовании.

### 9. Устранить гонки и отмену контекста в генерации AI

Лимит AI проверяется через `CountByUserSince`, а документ запроса создаётся позже; параллельные вызовы могут превысить лимит и вызвать несколько платных обращений к провайдеру. Для гостевых интерпретаций `singleflight` предотвращает повтор в пределах одного процесса, но callback использует `ctx` первого запроса: его отмена может сорвать генерацию для остальных ожидающих. Между несколькими экземплярами backend `singleflight` не координируется.

Ссылки: [ask.go:136](../../backend/internal/services/ask.go#L136), [ask.go:137](../../backend/internal/services/ask.go#L137), [ask.go:549](../../backend/internal/services/ask.go#L549), [ask.go:276](../../backend/internal/services/ask.go#L276), [ask.go:295](../../backend/internal/services/ask.go#L295).

**Рекомендация:** сначала реализовать атомарную AI-квоту из пункта 1. Затем отделить lifecycle генерации от контекста HTTP-клиента с ограниченным собственным timeout и явной политикой отмены, либо перевести AI на устойчивую задачу/очередь. Для многорепличного backend предусмотреть идемпотентный reservation/lock в общем хранилище.

### 10. Согласовать таймауты HTTP-ответа и AI-провайдера

По умолчанию `http.Server.WriteTimeout` равен 15 секундам, а HTTP-клиент OpenRouter ожидает до 20 секунд. Синхронный endpoint может не успеть записать ответ даже при успешном ответе провайдера; запросы также удерживают HTTP-ресурсы во время генерации.

Ссылки: [env.go:53](../../backend/config/env.go#L53), [env.go:65](../../backend/config/env.go#L65), [ask.go:788](../../backend/internal/services/ask.go#L788), [ask.go:794](../../backend/internal/services/ask.go#L794), [main.go:107](../../backend/main.go#L107).

**Рекомендация:** согласовать реальные production значения с полным бюджетом запроса, включая повторы и работу через relay. Для длинных генераций предпочтителен асинхронный процесс с polling по request ID; если оставлять синхронный режим, ограничить длительность контекста AI значением ниже server write deadline.

### 11. Ограничить пользовательский поиск и стабилизировать пагинацию

Поиск администраторов напрямую вставляет пользовательскую строку в Mongo `$regex` с опцией `i`, без экранирования metacharacters и ограничения длины. Поиск по произвольному подстрочному выражению плохо индексируется и может стать дорогим. Пагинация использует `skip` и вычисляет `(page - 1) * limit` до преобразования к `int64`; очень большие значения `page` могут переполнить целое число.

Ссылки: [user.go:139](../../backend/internal/repositories/user.go#L139), [user.go:173](../../backend/internal/repositories/user.go#L173), [admin.go:122](../../backend/internal/services/admin.go#L122), [reading.go:411](../../backend/internal/services/reading.go#L411).

**Рекомендация:** ограничить длину поисковой строки и экранировать её как literal pattern; при росте объёма перейти на нормализованные prefix-поля или Atlas Search. Ограничить максимальную глубину страницы, безопасно вычислять offset или использовать cursor/keyset pagination.

### 12. Гарантировать согласованность Mongo-документов и файловых ассетов

Создание колоды/рубашки сначала записывает документ со статусом `processing`, затем создаёт файлы и обновляет статус. Аварийное завершение может оставить документ в `processing`. При постоянном удалении сначала удаляется документ, а потом каталог файлов; ошибка файловой операции оставляет orphan-файлы без записи в Mongo.

Ссылки: [admin.go:319](../../backend/internal/services/admin.go#L319), [admin.go:323](../../backend/internal/services/admin.go#L323), [admin.go:339](../../backend/internal/services/admin.go#L339), [admin.go:542](../../backend/internal/services/admin.go#L542), [admin.go:564](../../backend/internal/services/admin.go#L564), [admin.go:568](../../backend/internal/services/admin.go#L568).

**Рекомендация:** ввести временное staging-хранилище и явные состояния операции, периодическую сверку/очистку зависших загрузок и безопасный порядок удаления. Удаление файла можно выполнять идемпотентно с повтором; Mongo-транзакция не включает локальную файловую систему, поэтому здесь подходит compensating action/outbox-подход, а не попытка общей транзакции.

## Поддерживаемость и качество изменений

### 13. Разделить крупные сервисы по сценариям и зависимостям

`AskService` объединяет сценарии AI-карты дня, общие расклады, кэш, лимиты, retry-политику и HTTP-клиент OpenRouter; `ReadingService` объединяет генерацию, историю, форматирование ответов и работу с URL-файлов; `AdminService` объединяет статистику, пользователей, настройки и lifecycle ассетов. Это затрудняет локальное изменение и тестирование отдельных частей.

Ссылки: [ask.go](../../backend/internal/services/ask.go), [reading.go](../../backend/internal/services/reading.go), [admin.go](../../backend/internal/services/admin.go).

**Рекомендация:** разбивать по ответственностям, а не только по размеру файла: например, provider/client и retry policy отдельно от AI use cases; reading generation/history отдельно от response assembler; admin asset lifecycle отдельно от users/settings/dashboard. Не вводить универсальный слой абстракции, если у сценариев разные правила.

### 14. Ввести узкие интерфейсы repository и тесты на конкурентные/интеграционные сценарии

Некоторые сервисы зависят напрямую от конкретных Mongo repository, из-за чего часть доменной логики проверяется только через helper-тесты. В backend есть полезные unit-тесты auth, времени, prompt и загрузки ZIP, но статический обзор не обнаружил repository/integration tests для индексов, атомарности обновлений и одновременных запросов.

**Рекомендация:** определить небольшие интерфейсы зависимостей на границе сервисов и использовать fake repositories в unit-тестах. Добавить проверки на: конкурентную выдачу карты дня; точное соблюдение лимитов; одновременное раскрытие разных карт; смену языка AI; обработку размеров изображений; индексы/запросы Mongo в отдельном integration suite. До начала рефакторинга закрепить текущий API контракт golden/contract тестами.

### 15. Централизовать фильтры Mongo, обработку ошибок и наблюдаемость

Фильтр пользователей повторно строится в `ListAdminUsers` и `CountAdminUsers`; повторная логика может постепенно расходиться. Ошибки сервиса преобразуются в generic 500 без явной структурированной записи исходной ошибки, а `/health` всегда отвечает `ok` и не проверяет доступность Mongo.

Ссылки: [user.go:139](../../backend/internal/repositories/user.go#L139), [user.go:173](../../backend/internal/repositories/user.go#L173), [helpers.go:113](../../backend/internal/handlers/helpers.go#L113), [health.go:25](../../backend/internal/handlers/health.go#L25), [main.go:36](../../backend/main.go#L36).

**Рекомендация:** вынести единый builder фильтра пользователя; добавить request ID и структурированное логирование ошибок с redaction секретов/токенов; разделить liveness и readiness, где readiness проверяет Mongo с коротким timeout. Для горячих запросов собирать latency и `explain`-планы до добавления индексов.

## Рекомендуемый порядок работ

1. Закрыть production-конфигурацию JWT, ограничить body/image ресурсы и убрать временные загрузки из публичного каталога.
